# 听书改进移植到线上分支（2026-10-08）

线上跑的是本分支：分段播放器先出声，能放原生 HLS 的设备再在句子边界接到连续音频（Queue 后台合成）。master 上那一版听书改进（PR #21）是按纯分段播放器写的，这次把其中线上还没有的部分移植过来，架构以线上为准。

移植过程中本分支合入了 PR #22（撤回 PR #20 的自写 MPEG-TS 封装和「直接从原生 HLS 起播」，见 `LISTENING_REGRESSION_2026-10-08.md`）。这里的改动都建在撤回之后的版本上，没有带回 PR #20 的封装、起播方式和重连逻辑；只恢复了其中一处跟封装无关的小修正：`liveLocationAt` 给媒体时间加 0.1 毫秒，精确跳到一句开头时不会因为微秒取整落回上一句（换章、15 秒跳转、本章结束后都要靠它）。

## 移植了什么

- **合成可靠性**：Edge 连接加 `muid`、10 秒无消息算超时；单片失败换条连接重试（最多 3 次，带抖动）；`/api/tts` 读不出来的文本回 422、服务问题回 503 并写日志。连续音频的 Queue 任务也用同一套单片重试，全是符号的片直接补静音、不送去合成。
- **停顿**：文字带结构（format 2：段落、标题、换章用 1/2/3 个换行），拼接时按帧裁掉每片结尾多余的自带静音、需要时补静音帧：句末约 0.66 秒、换段 0.8、标题 1.1、换章 1.8。新客户端建会话、调 `/api/tts` 都带 `format: 2`；老客户端不带，Worker 照旧处理，缓存键按 format 分开，互不串。
- **老路径分段**：起播 360 字、开播就预取 1500 字，之后 4800 字一批（以前是 360 字直接接 4800 字，长批次合成要四十多秒，起播半分钟左右必卡一次）。
- **系统打断**：来电、Siri、拔耳机只会暂停 audio 元素、不通知页面。以前状态还停在「在播」，锁屏的播放键（走 Media Session，只在没在播时才继续）按了没反应；现在两条路都监听 `pause` 同步成暂停，不自动续播（拔了耳机不该外放），锁屏、耳机的播放键接着放同一路音频。
- **云端失败**：先等 1.5 秒重试一次，再失败才用系统声音顶上；冷却 30 秒起翻倍、最多 5 分钟，冷却到点后系统朗读每读一块顺手试一次云端，通了下一块自动换回。以前一失败就整场都是系统声音，直到用户手动重新开播。
- **15 秒跳转**：按真实音频时间轴跳（以前是 ±2 句，长句短句差很多），锁屏进度条按目录项一章一章算、能拖（`seekto`）。
- **定时关闭**：到点暂停而不是停止（迷你播放条和位置都留着），加了 60 分钟，播放页显示倒计时；「本章结束后」按目录项算（续页算在内），在换章前的静音里停、位置挪到下一章开头。以前为了这个会不让连续音频接手、分段也不跨章切。停点判断在记进度之前：熄屏后进度回调来得晚、已经读过停点时，也不会先把下一章记成进度。
- **读音纠正**：设置 →「朗读音色」→「读音纠正」，只改送去合成的文字。
- **系统音色**：退回系统朗读时优先挑公认好听的中文音色和本机音色；安卓上不再用 pause/resume 保活（安卓上 pause 等于结束）。

## 没有移植的

- master 那一版的本机持久缓存（Cache Storage）和「离线缓存后面 3 章」、全书固定网格分段：它们是为纯分段播放器设计的，跟线上的连续音频会话（音频在 R2、按会话生成）对不上，硬搬会多出一套并行的缓存。
- 没有动连续音频的封装和接手、退回的时机：那是 PR #22 刚撤回、还在用真机日志查的部分。

## 验证

- `npm run lint`、`npm run typecheck`、`npm test`（含 build 和 Cloudflare 产物校验）：284 项单测全过。新增 `tests/speech-structure.test.ts`、`tests/worker-speech.test.ts`、`tests/live-hls-structure.test.ts`（结构化会话整理过停顿的 packed MP3 分片连同播放列表用 FFmpeg 完整解码；老客户端建的会话原样不动）。
- `tests/speech-chapter-browser.mjs`：40 项浏览器检查全过（真实《豆棚閒話》文本 + Chromium 真解码 MP3；HLS 控制流程用 MP3 替身，不等于 iPhone 实测）。替身 MP3 的路由补回了 Range 支持：不支持的话 Chromium 根本跳不动（`seekable` 为空），换章「跳过去」的检查其实没跳成。原来的「本章结束后停止」改成「暂停在下一章开头、用连续音频」；新增系统打断同步暂停、结构化文本、15 秒跳转、计时到点暂停、云端失败重试 → 系统声音 → 冷却后自动换回的检查。
- `npm run deploy:dry-run` 通过。

## 后续：关掉原生 HLS 接手（同日）

用户反馈「听一会儿就停一下、转圈加载」。查线上遥测（D1 `audio_telemetry`，只有播放事件和计时，没有正文）：这次发布后的那一场，开播 12.5 秒时切到原生 HLS，Safari 拿了第 0、1 片，`readyState` 一直是 1、`buffered` 为空，8 秒后超时退回分段，再重新合成一段才继续出声。往前翻，2026-10-02 起 iPhone 上 7 次接手（PR #20 前的格式、撤回后的格式、这次的版本都在内）全部是同样的结局，一次都没有 `playing`；PR #20 的 MPEG-TS 那几场倒是出过声，但同样会卡，已经撤回。也就是说连续音频从来没在用户手机上真正放出来过，大家听的一直是分段，只是每场都白卡一次。

处理：接手默认关掉（`liveHandoverEnabled()`），能放原生 HLS 的设备也不再建会话，分段一路播下去；Worker 那边不动，老客户端照旧。排查时在设备上 `localStorage.setItem("moting:live-hls", "1")` 打开。浏览器测试加了默认关闭的场景（不建会话、不换源、不转圈），HLS 场景改为手动打开后再测。
