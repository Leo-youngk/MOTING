## 已知限制

- 云端预览容器没有稳定的设备系统语音，不能据此评价音色或后台连续性；声音与可用语种必须在目标手机/电脑上验证。
- iOS 可能在锁屏、切到后台或省电模式下暂停网页语音，PWA 不能保证与原生音频播放器相同的后台策略。
- 扫描 PDF 暂不含 OCR；双栏、公式密集或复杂排版 PDF 的段落还原可能不理想。
- DRM EPUB 无法解析。
- 本版不含云端同步、书库导出、跨设备迁移或云端高质量 TTS。
- 数据依赖浏览器本地存储，清理站点数据会删除书库。

## 建议的真机验收

在目标 iPhone、Android 和桌面浏览器分别检查：

1. 安装到主屏幕。
2. 导入一册真实 EPUB 和一册真实文字 PDF。
3. 选择中文系统语音，以 1.0×、1.25×、1.5× 连续播放至少十分钟。
4. 测试锁屏、耳机控制、来电/闹钟打断后的恢复行为。
5. 关闭并重开应用，确认阅读与听书位置分别恢复。

# 划线修复（第一阶段补丁）

用户反馈真机上划线有问题。没有 iPhone 可驱动，改为重审手势时序并在模拟环境补齐上一轮漏掉的事件。

## 找到的两个问题

### 1. 抬手后浏览器补发的 click 把刚选出来的选区清掉了

真机时序：`pointerdown` → 460 ms 长按触发、选区出现 → 抬手 `pointerup` →
**浏览器补发 `click`** → `handleArticleClick` 看到 `textSelection.active` 为真 →
判定「点空白取消」→ `dismissSelection()`。用户看到的就是选区一闪即消。

上一轮没测出来，是因为测试只派发了 `pointerdown` / `pointerup`——
合成的指针事件不会产生 `click`，恰好绕开了这条路径。这次补上 `MouseEvent("click")`
后一次复现。

修法：长按成功选中时置一个一次性标记，正文点击处理先消费它；新手势的
`pointerdown` 会把标记作废，所以不会误吞后续正常的点击。

### 2. `user-select: none` 是个高风险赌注，换成 selectstart 拦截

原实现靠 `user-select: none` 压住系统选择菜单。但 WebKit 下正文一旦不可选，
`caretRangeFromPoint` 就不再下探到文本节点——那意味着长按按坐标根本找不到字，
**划线功能整个没反应**。这条在 Chromium 上测不出来（行为不同），属于测不到但赌不起的地方。

改成：正文保持可选，用 `selectstart` 的 `preventDefault` 拦住原生选择的启动，
并在 `selectionchange` 里收掉漏网的原生选区。最坏情况从「功能全废」降级成
「多出一层系统菜单」。

## 回归结果（Chromium，375×812 移动端模拟）

| 检查 | 结果 |
| --- | --- |
| 长按 → 抬手 → 补发 click | 选区与菜单仍在（修复前：清零） |
| 之后再轻点别处 | 选区正常取消，说明标记没有误吞后续点击 |
| 正文内 `selectstart` | `defaultPrevented === true` |
| 脚本强行建立的原生选区 | 被收掉，长度归零 |
| `npm test` | 98 项通过 |

## 本次暴露的工具环境陷阱（影响上一轮结论）

页面不绘制时，**滚动后上半屏的命中测试数据是陈旧的**：同一段文字，
`caretRangeFromPoint` 在 y > 440（最后绘制过的区域）能下探到文本节点，
y < 440 一律只返回 `<p>` 且 offset 恒为 0。

上一轮据此一度误判为「`user-select: none` 破坏了 caret 定位」。
**结论**：在这个环境里量 caret / elementFromPoint 之前，必须先确认测点落在新鲜绘制区，
或干脆先探测一个能下探到文本节点的点再用。

## 仍然只能真机确认

- iOS 上 `selectstart` 的 `preventDefault` 是否真能压住长按选择与系统菜单。
- 长按 460 ms、移动容差 10 px、手柄触控抬升 14 px 三个参数的手感。
- 手柄拖动与页面滚动的抢手势。
- WebKit 的中文分词边界（`Intl.Segmenter`）与 Chromium 的差异。

# 手柄修复（用户反馈：拖不动 / 选不准）

用户在 iPhone 上确认长按和选区本身正常，问题出在手柄。查出三处。

## 1. 触控区只有 30×21，圆球还画在盒子外面

手柄原本是「2px 竖线 + 左右各 14px 透明边框」，可点区域 30×21，远低于 44×44。
更要命的是那颗圆球用 `top: calc(knob / -2)` 定位，**有一半在按钮盒子之外**——
而用户瞄准的正是那颗球，等于瞄着一个不可点的地方按。

改成 44 宽、行高 + 上下各 12 的透明触控盒，竖线和圆球用伪元素画在盒子里面，
视觉不变。实测 44×46，瞄准圆球时 `elementFromPoint` 能命中 `.selection-handle--end`。

## 2. 两个手柄的触控盒几乎完全重叠

初选往往只有一两个字，两端相距不到 20px。两个 44px 的盒子若都以锚点居中，
重叠掉 40 多 px，捏哪头全凭运气。

改成盒子各自向外偏 75%：起点偏左、终点偏右。实测在 11px 宽的选区上，
重叠从约 44px 降到 11px（选区本身就这么宽），正常宽度的选区则完全不重叠。
偏移方向也正好对上「往左拉起点、往右拉终点」的直觉。

## 3. 固定抬升 14px 对两个手柄方向相反

拖动时原本把判定点统一上抬 14px。但起点手柄的球在行**上方**、终点的在行**下方**，
同一个补偿对其中一头正好是反的，会整整偏掉一行——这就是「选不准」。

改成在按下那一刻量一次手指与手柄锚点的差值（抓取偏移），整段拖动沿用。

## 4. 顺带修掉：拖动时翻出上一次划线的颜色菜单

`activePopup` 在自定义选区拖动期间（anchor 为 null）会回退到 `popup`，
把之前划线留下的「黄/绿/蓝/粉 + 想法/复制/删除」翻出来，挡着正在选的正文。
规则改成：自定义选区活着时只认它自己，拖动期间什么都不显示。

## 回归结果（Chromium，375×812 移动端模拟）

| 检查 | 结果 |
| --- | --- |
| 手柄触控区 | 44×46，两个都达标 |
| 瞄准圆球点击 | 命中 `.selection-handle--end` |
| 两手柄触控盒重叠 | 11px（选区宽度本身即 11px），原为几乎全重叠 |
| 拖动生效 | 选区 11px → 115px |
| 跟手精度 | 选区右缘与手指偏差 2–6px（单字宽约 19px） |
| 拖动中菜单 | 让开（null） |
| 松手后菜单 | 回到 划线/想法/复制/更多 |
| `npm test` | 98 项通过 |

## 仍然只能真机确认

- 44×44 触控区在真手指下是否够用（模拟环境只能验证几何，验证不了手感）。
- iOS 下 `setPointerCapture` + `touch-action: none` 能否稳定压住页面滚动。
- 拖到屏幕上下边缘时的自动滚动速度是否合适。

# 真机录屏定性：selectstart 拦不住 iOS 原生选择

用户提供了 iPhone 主屏幕 PWA 的 16 秒实测录屏（592×1280），逐帧看完，结论推翻了上一轮的赌注。

## 录屏里看到的

| 时间点 | 现象 |
| --- | --- |
| 1.5 s | 长按成功。墨听自己的选区（「我有」两字）、两个手柄、浮条「划线/想法/复制/更多」都正常出现 |
| 2.0 s | **iOS 原生菜单**「拷贝 \| 查询 \| 翻译 \| 搜索网页 \| ›」冒出来，整条盖住我们的浮条 |
| 2.5 s | 出现一大片跨多个段落的原生选区，和我们那一小块选区同时存在 |
| 8.5 s | **iOS 原生放大镜（loupe）**出现，压在浮条上 |
| 15.5 s | 原生菜单「拷贝 \| 翻译 \| 学习… ›」再次覆盖浮条，只剩最左边的「划线」露出来 |

也就是说：**iOS 的原生选区、放大镜、系统菜单一整套都在跑**，和墨听自己的选区并存。
用户拖到的其实是原生那一套手柄，所以看起来「手柄拖不动、选区乱跳」。

## 结论

上一轮把 `user-select: none` 换成脚本里 `preventDefault` 掉 `selectstart`，理由是
「万一 WebKit 下 `caretRangeFromPoint` 不肯下探到文本节点，功能会整个废掉」。
真机证明这个替代方案**完全不起作用**——iOS 的长按选择根本不走可被取消的 `selectstart`。

同时，第一版（用的就是 `user-select: none`）在真机上长按是能选出东西的
（当时用户的反馈是「手柄拖不动/选不准」，不是「长按没反应」），
说明那个担心的前提在这台设备上并不成立。

## 改法

1. CSS 改回 `user-select: none`——这是 WebKit 下唯一真正管用的开关。
2. 保留一层兜底：取 caret 时若落点不在句子上，临时把正文放开成可选、
   同步量一次、立刻收回（`caretInArticle`）。整段不让出事件循环，
   用户来不及在这个缝里拉出原生选区。万一真遇到那种 WebKit 版本，功能不至于全废。
3. `selectstart` / `selectionchange` 那两个监听留着当额外保险，成本为零。

## 回归结果（Chromium，375×812）

| 检查 | 结果 |
| --- | --- |
| 正文 user-select | none |
| 长按取词 | 成功（`caretRangeFromPoint` 在不可选元素上照常工作） |
| 手柄触控区 | 44×45 ×2 |
| 拖动跟手偏差 | 6 px |
| 拖动中菜单 | 让开 |
| 松手后菜单 | 划线/想法/复制/更多 |
| 原生选区残留 | 0 |
| 兜底路径的样式还原 | 无内联残留，计算值仍为 none |
| `npm test` | 98 项通过 |

## 仍需真机复核

- 原生菜单、放大镜是否彻底消失。
- 上一轮的手柄改动（44×44 触控、圆球移进盒内、触控盒外偏、抓取偏移跟手）
  在真机上从未被真正验证过——之前每次拖动都被原生选区劫走了。

# 第二段真机录屏：原生干扰已消除，选区渲染两处缺陷

用户提供第二段 iPhone PWA 录屏（25.6 秒），验证 `user-select: none` 那一版。

## 好的部分

- **iOS 原生菜单、放大镜、原生选区全部消失**，屏幕上只剩墨听自己的一套。
- 长按取词正常，手柄正常，浮条「划线/想法/复制/更多」正常。
- 划线成功落地：整段黄色标记跨多行正确渲染，滚动后仍在。

`user-select: none` 是对的，这条不用再摇摆。

## 逐帧看出来的两处缺陷

### 1. 选区是一条条横杠，行间留黑缝

原始分辨率裁图看得很清楚：选区底色只覆盖字形那一条（约 21px），
而一行占 36.1px，行与行之间留着约 15px 没涂，整片选区呈条纹状，
跟系统选区那种连续色块完全不是一回事。

原因是 `range.getClientRects()` 给的是**字形盒**不是**行盒**。

改法：新增 `fillLineBoxes()`，把同一行的碎片合并成一条，再按相邻行的实际间隔
补齐到整行高。行距按邻行间隔算而不是取一个全局行高，正文和标题各自不同的
行高都能补对；只有一行时才退回读到的 `line-height`。

### 2. 长选区时菜单压在选中的正文上

录屏第 10 秒：选区从屏幕上部一直拉到中段，菜单翻到「下方」后正好盖住选中的
第二、三行。原因是锚点永远取选区**第一行**，「下方」是相对第一行说的。

改法：新增 `placeForSelection()`，先按选区顶端试上方；一旦判定要翻到下方，
就改用选区**底端**重新摆一次，并优先保持在下方。菜单因此只会出现在整片选区的
外侧，不会压住正文。

## 仍需真机复核

- 选区色块是否连续、观感是否接近系统选区。
- 长选区时菜单是否确实落在选区外侧。
- 手柄手感（44×44 触控、抓取偏移跟手）——前两轮都被原生选区劫走，从未真正验证过。
