# PR #20 听书退步调查与撤回

用户反馈发布后更差。2026-10-07 发布后的 281 条音频事件证实了退步，不能继续把 PR #20 的自动测试当作手机验收。

## 已确认的现象

- 14:10–14:12 UTC 多次原生起播请求从第 5 个媒体分片开始，实际播放时钟从约 27 秒开始，而不是计划开头。
- 17:21 UTC 的会话在后台起播时保持 currentTime=0、readyState=1、buffered=[]；回到前台重新播放后，首个媒体请求是第 19 片，playing 事件 currentTime=101.352。
- 同一会话服务端继续准备到 1357.704 秒，手机在 123.59 秒停留，buffered 只有数秒或为空。该会话在 17:21:14 建立，17:24:58 才记录到第一次 playing；此事件不证明实际声音质量。
- 另一会话记录到 MediaError=3（解码错误）。没有下载或检查用户私人正文、分片音频。

## 代码与验证缺口

PR #20 同时更换 MP3/HLS 封装为自行编写的 MPEG-TS，并移除了原生 HLS 的显式定位，只依赖 EXT-X-START。客户端未验证原生实际起播位置，也未覆盖播放时钟与缓冲范围不一致的事件。新的直接原生起播还撤掉了原来的首段快速播放路径，以上错误因而会从第一次点击就阻止出声。

21 项 Chromium 交互检查以普通 MP3 替代原生 HLS，不会测试 AVFoundation 的分片解码、直播边缘选择或后台起播。FFmpeg 的 HLS 测试明确设置了 live_start_index=0 和 prefer_x_start=1，因此它的连续解码结果也不能证明 Safari 会按同样的位置起播。259 项单元测试同样不覆盖这些手机媒体行为。

日志足以确认起播定位与原生缓冲链路失败，但尚不足以将 MediaError=3 精确归因到某个 MPEG-TS 字段或编解码器兼容条件。此前把所有周期停顿归因到时间戳重置，并宣布完整修复，证据不足。

## 本次处理

撤回 PR #20 的播放器与封装改动，恢复此前的快速首段播放和原有音频格式。保留实际 buffered 范围和 MediaError 事件诊断，版本为 2026-10-08-rollback-v5，PWA shell 为 v22。撤回版本不继续处理 v4 格式的队列任务，旧格式会话仍兼容；失败的 v4 会话返回明确的 410，需新开始一次听书。

本次撤回用于消除已确认的新增退步，不等于解决此前的间歇停顿或完成 iPhone 锁屏长播验收。后续媒体方案必须检查真实原生 HLS 起播位置、持续推进的时钟、缓冲范围、后台到前台切换及解码错误，不能再用 MP3 替身或强制 FFmpeg 起点作为替代证明。

回退验证：255 项 Node 测试、类型检查与变更文件 ESLint 通过。回退后的 Chromium 播放器交互检查也通过，覆盖快速首段、跨章、暂停、错误恢复和睡眠停止；这些结果仅说明回退未破坏所测流程，不作为原生 Safari 或锁屏验收。新增测试确认 v4 任务不会改写旧格式状态，失败会话返回 410，缓冲范围和解码错误诊断仍保留。
